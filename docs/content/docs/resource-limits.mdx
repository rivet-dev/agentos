Limits are part of the durable actor config and are applied by the sidecar
during VM creation.

<CodeSnippet file="examples/embedded/limits.ts" />

Use `limits.tls.maxBufferedBytes` to bound TLS plaintext buffering.
`limits.execution.completedTtlMs` and `limits.execution.maxCompletedExecutions`
bound retained completed language executions. `limits.execution.liveExecutionWarningThreshold`
sets the live execution count that triggers a warning, not a rejection.
These fields are optional in both Rust and TypeScript Core; omission keeps the
sidecar default.

Every queue, buffer, timeout, and resource collection has a bounded default.
Near-capacity conditions emit `vm.limitWarning`; exhausted limits fail
with a typed error naming the limit and the field used to raise it.

In the library, `onLimitWarning` receives the same warning. Limits that apply
to the whole sidecar process, such as `runtime.executor.maxActiveVms`, are set
on a dedicated sidecar created with `AgentOs.createSidecar()`.

`limits.reactor.shutdownDeadlineMs` bounds the SQLite close wait and subsequent
resource drain together. Process termination and filesystem flushing happen
before this budget. If close exceeds the deadline,
VM shutdown reports a typed `timeout` with the limit name instead of reporting
a clean stop. Close completion can no longer be confirmed, so the generation
stays quarantined—even if local resource counts reach zero—until the sidecar
worker restarts. Quarantined generations count toward VM admission capacity.
The hosted actor also has a fixed ten-second shutdown wait; raising the sidecar
deadline does not extend it. The runtime test API has a separate one-second
disposal wait. Exceeding either client wait reports a timeout, not confirmed
shutdown; the remote operation may still be running.

The sidecar waits for its VM-owned host directories to be removed and the
cleanup task's resource reservations to be released before reporting successful
disposal. Cleanup uses the shared blocking executor. Its admission is governed
by `runtime.blocking.maxJobs`, `runtime.blocking.maxQueuedJobs`, and
`runtime.blocking.maxQueuedBytes`. Tracked cleanup records are capped by
`runtime.resources.maxCapabilities` and emit a sidecar warning near that cap.

Once cleanup is activated, cancellation of the request waiting for it does not
cancel the cleanup. During protocol shutdown, if the sidecar cannot confirm
cleanup by its original shutdown deadline, it reports
`ERR_AGENTOS_VM_PATH_CLEANUP_UNCONFIRMED`. Directory removal can still be in
progress when that failure is reported.

The hosted action envelope, filesystem transfer, process replay, network, and
software-cache ceilings are listed in
[Hosted Actor Limits](/agentos/docs/actor-limits).

Guest JavaScript has a V8 heap cap and a separate cap for `ArrayBuffer` memory.
Both use `limits.jsRuntime.v8HeapLimitMb`; Python uses
`limits.python.maxOldSpaceMb`. Exceeding a cap fails the execution and leaves
other VMs running. The sidecar can keep up to four prestarted V8 isolates;
`AGENTOS_V8_WARM_ISOLATES=0` disables that pool to reduce idle memory at the
cost of slower execution starts.

Replacing limits normally requires a runtime generation replacement. Graceful
process draining during replacement is a separately tracked follow-up.

JavaScript handle diagnostics retain at most 4,096 registrations and 256 KiB of
UTF-8 handle IDs and descriptions per execution bridge. The trusted host can
raise these limits with `AGENTOS_JS_MAX_HANDLE_DESCRIPTIONS` and
`AGENTOS_JS_MAX_HANDLE_DESCRIPTION_BYTES` before starting the sidecar. Guest VM
environment variables cannot change them. Zero, invalid, or overflowing host
values produce a host warning and use the bounded defaults.

At 80% capacity, `javascript_handle_descriptions` and
`javascript_handle_description_bytes` emit host limit warnings. Registration
beyond either cap fails with `ERR_AGENTOS_RESOURCE_LIMIT`; replacing an existing
ID charges only the changed bytes, and unregistering releases its budget.
Listing preflights JSON escaping against the bridge response ceiling and fails
with `ERR_AGENTOS_BRIDGE_RESPONSE_LIMIT` before copying an oversized list.
Unregister handles or reduce these host limits if the list exceeds that ceiling.

Promise rejection delivery has a fixed capacity of 1,024 pending events per V8
execution and 1,024 listener dispatches per checkpoint drain. The host warns at
80% capacity and fails with `ERR_AGENTOS_UNHANDLED_REJECTION_LIMIT` if either
bound is exceeded. Reduce pending rejections or recursive rejection handlers to
stay within this bound. There is no runtime option to raise it; changing the
capacity requires rebuilding the runtime. Reported promises are not retained by
a runtime history collection.

Guest Node HTTP parsing uses `limits.http.maxChunkSizeLineBytes` (default
16416 bytes) for a retained chunk-size line and
`limits.http.maxPendingResponseBytes` (default 262144 bytes) for raw response
bytes retained while a reader is paused. These are separate from the total
buffered fetch-response limit. Raising the whole-line limit does not raise
Node's fixed 16 KiB chunk-extension compatibility limit.

`limits.jsRuntime.maxReadlineHistoryEntries` (default 1024) bounds the caller's
readline `historySize`. The requested default remains 30; `historySize: 0`
disables history. Lower `historySize` or raise the trusted VM ceiling if a
request exceeds it. All three settings are positive safe integers supplied at
VM creation in Rust or TypeScript; they apply to that VM's executions and do
not change other VMs or standalone executor defaults. They cannot be changed
through guest globals.

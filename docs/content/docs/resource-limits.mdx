Pass a `limits` tree in the VM's configuration. The sidecar applies it when the
VM starts. Near-limit pressure is reported as the `vm.limitWarning` event on a
hosted VM, or through `onLimitWarning` in the library.

<CodeGroup>

```ts Hosted @nocheck
import { createAgentOsClient } from "@rivet-dev/agentos";

const client = createAgentOsClient({ endpoint: "https://api.rivet.dev" });
const vm = client.agentOS.getOrCreate(["my-vm"]);

await vm.v1.config.set({
	config: {
		limits: {
			tls: { maxBufferedBytes: 2048 },
			execution: { completedTtlMs: 60_000, liveExecutionWarningThreshold: 32 },
			agentosPackages: { maxMounts: 8192 },
		},
	},
});

// Changed limits apply to the next VM generation.
await vm.v1.vm.restart({});
```

</CodeGroup>

Use `limits.tls.maxBufferedBytes` to bound TLS plaintext buffering.
`limits.execution.completedTtlMs` and `limits.execution.maxCompletedExecutions`
bound retained completed language executions. `limits.execution.liveExecutionWarningThreshold`
sets the live execution count that triggers a warning, not a rejection.
These fields are optional; omission keeps the sidecar default.

Process output replay is also sidecar-owned. The defaults retain
up to 1,024 events or 1 MiB for each opted-in process, return at most 256 events
or 768 KiB per read, and retain at most 1,024 replay records per VM. Override
them with `limits.process.outputReplayEvents`, `outputReplayBytes`,
`outputReplayPageEvents`, `outputReplayPageBytes`, and `maxOutputReplays`.
Page limits cannot exceed their corresponding retention limits. Omitting a page
bound in `process.readOutput` uses the VM's configured limit; explicit zero or a
value above the limit is rejected.

Every queue, buffer, timeout, and resource collection has a bounded default.
Near-capacity conditions call `onLimitWarning`; exhausted limits fail with a
typed error naming the limit and the field used to raise it.

`limits.reactor.shutdownDeadlineMs` bounds the SQLite close wait and subsequent
resource drain together. Process termination and filesystem flushing happen
before this budget. If close exceeds the deadline,
VM shutdown reports a typed `timeout` with the limit name instead of reporting
a clean stop. Close completion can no longer be confirmed, so the VM stays
quarantined until the sidecar process restarts, even if local resource counts
reach zero. Quarantined VMs count toward VM admission capacity.

Socket writes between processes in the same VM share the
`limits.resources.maxSocketBufferedBytes` budget. When the budget is full, a
write waits for the reader to drain it, like a Node.js socket write. If the
reader does not drain it within `limits.reactor.operationDeadlineMs`, the
write fails with `ETIMEDOUT` and an error that names that limit.

`limits.reactor` bounds the sidecar reactor: its queues
(`maxCapabilities`, `maxReadyHandles`, `maxTasks`, `maxHandleCommands`,
`maxBridgeCalls`, `maxAsyncCompletions`, `maxBlockingJobs`), their byte
budgets, its scheduling quanta, `shutdownDeadlineMs`, and
`operationDeadlineMs` (30 seconds by default), which bounds each host-backed
operation. Every value must be greater than zero.

Limits are fixed for the life of a VM. To change them on a hosted VM, update
the config and call `v1.vm.restart`. In the library, dispose the VM and create
a new one with the new limits. The hosted actor also has a fixed ten-second
shutdown wait; raising the sidecar deadline does not extend it.

## Sidecar limits

Library VMs share a sidecar process by default. Limits that apply to the whole
process, such as `runtime.executor.maxActiveVms`, are set when creating a
dedicated sidecar with `AgentOs.createSidecar()`, as in the example above.

Each library request to the sidecar must fit in one protocol frame. The sidecar
reports its frame limit (16 MiB) when the client connects, and the limit is not
configurable. The client rejects a larger request with `SidecarFrameTooLarge`
before it sends it, so the sidecar and the other VMs on it keep running.
`writeFile` base64-encodes binary content, so one call carries at most about
12 MiB of binary data. `writeFiles` sends raw bytes and splits a large batch
into several requests by the frame limit and the per-request file limit
(16) that the sidecar reports when the client connects, so only each single file must
fit in one frame (about 16 MiB). To move larger files, split them into several
files or mount a host directory.

The sidecar runs at most 128 requests at once from one client. Priority
requests have a separate limit of 128: VM dispose, process kill and signal,
execution cancel and delete, stdin writes and closes, and PTY resizes. A flood
of other work, such as VM creation, never delays them, so a busy sidecar can
always dispose a VM or drive a running process. VM creates use at most 64 of
the 128 slots and wait in their own queue, so a burst of creates cannot delay
other VMs' calls. A create above that cap waits in its queue, where the queue
limits below apply (`ERR_AGENTOS_IN_FLIGHT_CREATE_REQUEST_LIMIT` names the cap
internally and is not returned to callers). These limits are not configurable.

The sidecar queues requests above a limit, in arrival order, with separate
queues for ordinary requests, VM creates, and priority requests. Up to 256
requests (64 MiB) wait in each queue. An ordinary request waits at most 5
seconds; a VM create or a priority request waits at most 30 seconds, since a
burst of creates or a mass teardown takes longer. Teardown (VM dispose, process
kill and signal, execution cancel and delete) never fails because the queue
holds 256 requests: a rejected teardown would leak a VM or a process, and
teardown is already bounded by the VMs and processes that exist and by the
64 MiB limit. A request that finds the queue full fails with
`ERR_AGENTOS_REQUEST_QUEUE_LIMIT`, and a request that waits too long fails with
`ERR_AGENTOS_REQUEST_QUEUE_TIMEOUT`. Both errors are retryable (`EAGAIN`) and
name the limit in `configuration_path`. The queue size, bytes, and deadlines
are fixed in the shipped sidecar; no client option changes them.

Each client holds up to 1024 stdin writes per process until the process's
launch is confirmed, so writes made right after `spawn()` arrive in order. A
write beyond that fails with a retryable `ERR_AGENTOS_RESOURCE_LIMIT`
(`process_stdin_queue_entries`); await earlier writes before sending more.

The Rust client fans sidecar events out through a buffer of 4,096 events. If an
`exec` falls further behind than that, it fails with `ERR_AGENTOS_OUTPUT_LAGGED`
instead of returning incomplete output; output callbacks and streams log the
skipped chunks. Recover the output with `read_process_output`. The TypeScript
client delivers every byte written before a process exits to `onStdout` and
`onStderr`, including when the host is slow to drain them.

`dispose()` is one request: the sidecar stops the VM's running processes
(`SIGTERM`, then `SIGKILL`) and then removes the VM. If `dispose()` fails, the
VM can still be alive. Call `dispose()` again to retry.

When a sidecar starts, it removes temp directories that exited sidecars left
behind, for example after `SIGKILL`. It removes a directory only after that
sidecar's liveness lock proves it is gone, and at most 1024 entries per start;
later starts remove the rest.

### Isolate memory

Each V8 isolate that runs guest JavaScript or Python has two memory caps of the
same size: one for the V8 heap and one for `ArrayBuffer` memory, which also
backs typed arrays, `Buffer`, and `SharedArrayBuffer`. The size is
`limits.jsRuntime.v8HeapLimitMb` for JavaScript (128 MiB by default) and
`limits.python.maxOldSpaceMb` for Python. A script that goes past the heap cap
fails with `execution_heap_limit_exceeded`. An allocation that goes past the
`ArrayBuffer` cap throws `RangeError: Array buffer allocation failed`, and the
sidecar reports the `v8_array_buffer_bytes` limit warning. Other VMs on the
sidecar keep running in both cases.

In JavaScript, WebAssembly memory and buffers that hold data from the host,
such as file contents, have a third cap of the same size. V8 checks it during
garbage collection. A script that goes past it fails with
`execution_heap_limit_exceeded`, and the sidecar reports the
`v8_external_memory_bytes` limit warning. Python keeps its interpreter memory
in WebAssembly, so this cap does not apply to Python. Shared WebAssembly
memory, resizable `ArrayBuffer`s, and growable `SharedArrayBuffer`s are not
counted toward any cap.

### Sidecar memory

On Linux with glibc, the sidecar returns memory freed by a disposed VM's V8
isolates to the OS shortly after disposal. At startup it also sets the glibc
trim threshold to 1 MiB and the mmap threshold to 4 MiB, so memory freed by
stopped processes does not stay in per-thread allocator arenas. A
`MALLOC_TRIM_THRESHOLD_` or `MALLOC_MMAP_THRESHOLD_` value in the sidecar's
environment replaces the matching setting.

All isolates share one copy of the V8 snapshot and of the runtime's
JavaScript bridge source. When a guest's event loop has received no work for
one second, the sidecar runs one memory-reducing garbage collection on its
isolate. It runs another only when the heap has doubled (by at least 8 MiB)
since the last one and at least 30 seconds have passed, so a guest that
serves requests with idle gaps does not pay for a full collection per gap.

The sidecar also keeps a pool of up to four pre-started V8 isolates so that
JavaScript and Python executions start faster. The pool stays resident while
the sidecar runs, at about 15 MiB per isolate. To cap it, set
`AGENTOS_V8_WARM_ISOLATES` to a value from `0` to `4` in the environment that
starts the sidecar. `0` disables the pool and trades memory for slower
execution starts.

The sidecar stores built V8 snapshots on disk so a new sidecar process does
not rebuild them: at most 16 files under `$XDG_CACHE_HOME/agentos/v8-snapshots`
(or `~/.cache/agentos/v8-snapshots`). Set `AGENTOS_V8_SNAPSHOT_CACHE_DIR` to
another directory, or to `off`, in the environment that starts the sidecar.
Script sources that snapshot-restored isolates share are kept while a cached
snapshot or a live isolate uses them, bounded to 64 MiB of copies. Unused
sources are freed first; when the sources in use leave no room, a new snapshot
fails with `ERR_AGENTOS_V8_SHARED_SOURCE_LIMIT` and processes load normally.

A helper process builds each snapshot. It is killed after 30 seconds
(`ERR_AGENTOS_V8_SNAPSHOT_HELPER_TIMEOUT`, and processes load normally), its V8
heap and its ArrayBuffer memory are each capped at 1 GiB, and its CPU time is
capped at the timeout. Set `AGENTOS_V8_SNAPSHOT_HELPER_TIMEOUT_MS` in the
environment that starts the sidecar to change the timeout.

## Embedded API

Limits apply to VMs created with `AgentOs.create()` and sidecars created with
`AgentOs.createSidecar()`. Read more in the
[embedded API quickstart](/agentos/docs/quickstart-embedded).

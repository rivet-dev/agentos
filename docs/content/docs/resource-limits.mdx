Limits are part of the durable actor config and are applied by the sidecar
during VM creation.

<CodeSnippet file="examples/embedded/limits.ts" />

Use `limits.tls.maxBufferedBytes` to bound TLS plaintext buffering.
`limits.execution.completedTtlMs` and `limits.execution.maxCompletedExecutions`
bound retained completed language executions. `limits.execution.liveExecutionWarningThreshold`
sets the live execution count that triggers a warning, not a rejection.
These fields are optional in both Rust and TypeScript Core; omission keeps the
sidecar default.

`limits.reactor` exposes optional queue, byte-budget, scheduling-quantum, and
operation/shutdown deadline overrides in both Core clients. Omitted fields use
the sidecar defaults. Values must be positive JavaScript-safe integers; unknown
fields and invalid values are rejected. Existing parent/child and frame-budget
constraints still apply. `operationDeadlineMs` bounds each host-backed operation
(30 seconds by default), including an undrained socket write.

`filesystem.writeFiles()` creates missing parent directories and returns one
result per input entry, in order. A failed entry does not stop later entries.
The clients split sidecar batches by its advertised entry cap (16) and
frame limit (16 MiB by default). File bytes are sent without base64 expansion; each single
file and its request metadata must still fit in one frame. A larger single
file returns a per-entry error. Split larger files or mount a host directory.
`filesystem.writeFile()` keeps its existing base64 encoding and frame limit.

Every queue, buffer, timeout, and resource collection has a bounded default.
Near-capacity conditions emit `vm.limitWarning`; exhausted limits fail
with a typed error naming the limit and the field used to raise it.

In the library, `onLimitWarning` receives the same warning. Limits that apply
to the whole sidecar process, such as `runtime.executor.maxActiveVms`, are set
on a dedicated sidecar created with `AgentOs.createSidecar()`.

`limits.reactor.shutdownDeadlineMs` bounds the SQLite close wait and subsequent
resource drain together. Process termination and filesystem flushing happen
before this budget. If close exceeds the deadline,
VM shutdown reports a typed `timeout` with the limit name instead of reporting
a clean stop. Close completion can no longer be confirmed, so the generation
stays quarantined—even if local resource counts reach zero—until the sidecar
worker restarts. Quarantined generations count toward VM admission capacity.
The hosted actor also has a fixed ten-second shutdown wait; raising the sidecar
deadline does not extend it. The runtime test API has a separate one-second
disposal wait. Exceeding either client wait reports a timeout, not confirmed
shutdown; the remote operation may still be running.

The sidecar waits for its VM-owned host directories to be removed and the
cleanup task's resource reservations to be released before reporting successful
disposal. Cleanup uses the shared blocking executor. Its admission is governed
by `runtime.blocking.maxJobs`, `runtime.blocking.maxQueuedJobs`, and
`runtime.blocking.maxQueuedBytes`. Tracked cleanup records are capped by
`runtime.resources.maxCapabilities` and emit a sidecar warning near that cap.

Once cleanup is activated, cancellation of the request waiting for it does not
cancel the cleanup. During protocol shutdown, if the sidecar cannot confirm
cleanup by its original shutdown deadline, it reports
`ERR_AGENTOS_VM_PATH_CLEANUP_UNCONFIRMED`. Directory removal can still be in
progress when that failure is reported.

The hosted action envelope, filesystem transfer, process replay, network, and
software-cache ceilings are listed in
[Hosted Actor Limits](/agentos/docs/actor-limits).

Guest JavaScript has a V8 heap cap and a separate cap for `ArrayBuffer` memory.
Both use `limits.jsRuntime.v8HeapLimitMb`; Python uses
`limits.python.maxOldSpaceMb`. Exceeding a cap fails the execution and leaves
other VMs running. The sidecar can keep up to four prestarted V8 isolates;
`AGENTOS_V8_WARM_ISOLATES=0` disables that pool to reduce idle memory at the
cost of slower execution starts.

Replacing limits normally requires a runtime generation replacement. Graceful
process draining during replacement is a separately tracked follow-up.

JavaScript handle diagnostics retain at most 4,096 registrations and 256 KiB of
UTF-8 handle IDs and descriptions per execution bridge. The trusted host can
raise these limits with `AGENTOS_JS_MAX_HANDLE_DESCRIPTIONS` and
`AGENTOS_JS_MAX_HANDLE_DESCRIPTION_BYTES` before starting the sidecar. Guest VM
environment variables cannot change them. Zero, invalid, or overflowing host
values produce a host warning and use the bounded defaults.

At 80% capacity, `javascript_handle_descriptions` and
`javascript_handle_description_bytes` emit host limit warnings. Registration
beyond either cap fails with `ERR_AGENTOS_RESOURCE_LIMIT`; replacing an existing
ID charges only the changed bytes, and unregistering releases its budget.
Listing preflights JSON escaping against the bridge response ceiling and fails
with `ERR_AGENTOS_BRIDGE_RESPONSE_LIMIT` before copying an oversized list.
Unregister handles or reduce these host limits if the list exceeds that ceiling.

A retained JavaScript isolate can keep at most 1,026 native contexts, including
its session/process roots and contexts retained through `node:vm` functions.
This fixed bound is separate from the 1,024-entry `node:vm` registry, which can
reset between calls. Near the family bound, the host logs
`WARN_AGENTOS_VM_CONTEXT_LIMIT`. At saturation, one collection first removes
unreachable contexts; if the family remains full, context creation fails with
`ERR_AGENTOS_VM_CONTEXT_LIMIT`. Release retained context/function references or
split the workload across VMs. There is no runtime override for this bound.
Collection at saturation can add latency; it does not execute queued guest jobs.

Promise rejection delivery has a fixed capacity of 1,024 pending events per V8
execution and 1,024 listener dispatches per checkpoint drain. The host warns at
80% capacity and fails with `ERR_AGENTOS_UNHANDLED_REJECTION_LIMIT` if either
bound is exceeded. Reduce pending rejections or recursive rejection handlers to
stay within this bound. There is no runtime option to raise it; changing the
capacity requires rebuilding the runtime. Reported promises are not retained by
a runtime history collection.

Guest Node HTTP parsing uses `limits.http.maxChunkSizeLineBytes` (default
16416 bytes) for a retained chunk-size line and
`limits.http.maxPendingResponseBytes` (default 262144 bytes) for raw response
bytes retained while a reader is paused. These are separate from the total
buffered fetch-response limit. Raising the whole-line limit does not raise
Node's fixed 16 KiB chunk-extension compatibility limit.

`limits.jsRuntime.maxReadlineHistoryEntries` (default 1024) bounds the caller's
readline `historySize`. The requested default remains 30; `historySize: 0`
disables history. Lower `historySize` or raise the trusted VM ceiling if a
request exceeds it. All three settings are positive safe integers supplied at
VM creation in Rust or TypeScript; they apply to that VM's executions and do
not change other VMs or standalone executor defaults. They cannot be changed
through guest globals.

## Sidecar limits

Library VMs share a sidecar process by default. Limits that apply to the whole
process, such as `runtime.executor.maxActiveVms`, are set when creating a
dedicated sidecar with `AgentOs.createSidecar()`, as in the example above.

Each library request to the sidecar must fit in one protocol frame. The sidecar
reports its frame limit (16 MiB) when the client connects, and the limit is not
configurable. The client rejects a larger request with `SidecarFrameTooLarge`
before it sends it, so the sidecar and the other VMs on it keep running.
`writeFile` base64-encodes binary content, so one call carries at most about
12 MiB of binary data. `writeFiles` sends raw bytes and splits a large batch
into several requests by the frame limit and the per-request file limit
(16) that the sidecar reports when the client connects, so only each single file must
fit in one frame (about 16 MiB). To move larger files, split them into several
files or mount a host directory.

By default, the sidecar runs at most 128 ordinary requests at once from one
client. Set `runtime.protocol.maxInFlightRequests` on the dedicated sidecar to
change that limit, together with sufficient terminal capacity. The shipped
sidecar derives ingress capacity from this explicit request budget and its
fixed waiting-queue size. When no `maxControlFrames` override is supplied, it
also reserves space for priority replies and heartbeat progress. An explicit
control-frame cap is never raised automatically. Priority
requests have a separate default limit of 128: VM dispose, process kill and signal,
execution cancel and delete, stdin writes and closes, and PTY resizes. A flood
of other work, such as VM creation, does not consume their admission slots.
VM creates use at most half the ordinary slots (64 by default, at least one)
and wait in their own queue, so a burst of creates does not queue ahead of
other VMs' calls. A create above that cap waits in its queue, where the queue
limits below apply (`ERR_AGENTOS_IN_FLIGHT_CREATE_REQUEST_LIMIT` names the cap
internally and is not returned to callers). The shipped sidecar keeps the
priority limit fixed; embedded Rust hosts can configure it through
`DriverProtocolConfig.max_in_flight_priority_requests`.

The sidecar queues requests above a limit, in arrival order, with separate
queues for ordinary requests, VM creates, and priority requests. Up to 256
requests (64 MiB) wait in each queue. An ordinary request waits at most 5
seconds; a VM create or a priority request waits at most 30 seconds, since a
burst of creates or a mass teardown takes longer. Teardown (VM dispose, process
kill and signal, execution cancel and delete) never fails because the queue
holds 256 requests: a rejected teardown would leak a VM or a process, and
teardown is already bounded by the VMs and processes that exist and by the
64 MiB limit. A request that finds the queue full fails with
`ERR_AGENTOS_REQUEST_QUEUE_LIMIT`, and a request that waits too long fails with
`ERR_AGENTOS_REQUEST_QUEUE_TIMEOUT`. Both errors are retryable (`EAGAIN`) and
name the limit in `configuration_path`. The queue size, bytes, and deadlines
are fixed in the shipped sidecar; no client option changes them. Embedded Rust
hosts can set `DriverProtocolConfig.request_queue_limit`, `request_queue_bytes`,
and `request_queue_deadline_ms`; create and priority queues always allow at
least 30 seconds.

Each client holds up to 1024 stdin writes per process until the process's
launch is confirmed, so writes made right after `spawn()` arrive in order. A
write beyond that fails with a retryable `ERR_AGENTOS_RESOURCE_LIMIT`
(`process_stdin_queue_entries`); await earlier writes before sending more.

The Rust client fans sidecar events out through a buffer of 4,096 events. If an
`exec` falls further behind than that, it fails with `ERR_AGENTOS_OUTPUT_LAGGED`
instead of returning incomplete output; output callbacks and streams log the
skipped chunks. Recover the output with `read_process_output`. The TypeScript
client delivers every byte written before a process exits to `onStdout` and
`onStderr`, including when the host is slow to drain them.

The host captures up to 16 MiB of combined stdout and stderr per call.
If output exceeds that budget, the call fails with
`ERR_AGENTOS_CAPTURED_OUTPUT_LIMIT`. Set `maxCapturedOutputBytes` in
TypeScript or `ExecOptions.max_captured_output_bytes` in Rust to raise it.
For larger output without retaining it in memory, spawn the process and stream
its output.

Native execution rejects per-run CPU overrides and requests for the legacy
`freeze` timing mode with `ERR_AGENTOS_UNSUPPORTED_EXECUTION_OPTION`.
Configure CPU time at VM creation. Set VM-level `highResolutionTime` in
TypeScript or `high_resolution_time` in Rust to control clock precision.
The legacy `off` option preserves the VM clock policy.

`dispose()` is one request: the sidecar stops the VM's running processes
(`SIGTERM`, then `SIGKILL`) and then removes the VM. If `dispose()` fails, the
VM can still be alive. A failed disposal is retained because repeating a partially completed teardown
is not safe; shut down the owning sidecar to confirm cleanup.

When a sidecar starts, it removes temp directories that exited sidecars left
behind, for example after `SIGKILL`. It removes a directory only after that
sidecar's liveness lock proves it is gone, and at most 1024 entries per start;
later starts remove the rest.

### Isolate memory

Each V8 isolate that runs guest JavaScript or Python has two memory caps of the
same size: one for the V8 heap and one for `ArrayBuffer` memory, which also
backs typed arrays, `Buffer`, and `SharedArrayBuffer`. The size is
`limits.jsRuntime.v8HeapLimitMb` for JavaScript (128 MiB by default) and
`limits.python.maxOldSpaceMb` for Python. A script that goes past the heap cap
fails with `execution_heap_limit_exceeded`. An allocation that goes past the
`ArrayBuffer` cap throws `RangeError: Array buffer allocation failed`, and the
sidecar reports the `v8_array_buffer_bytes` limit warning. Other VMs on the
sidecar keep running in both cases.

In JavaScript, WebAssembly memory and buffers that hold data from the host,
such as file contents, have a third cap of the same size. V8 checks it during
garbage collection. A script that goes past it fails with
`execution_heap_limit_exceeded`, and the sidecar reports the
`v8_external_memory_bytes` limit warning. Python keeps its interpreter memory
in WebAssembly, so this cap does not apply to Python. Shared WebAssembly
memory, resizable `ArrayBuffer`s, and growable `SharedArrayBuffer`s are not
counted toward any cap.

### Sidecar memory

On Linux with glibc, the sidecar returns memory freed by a disposed VM's V8
isolates to the OS shortly after disposal. At startup it also sets the glibc
trim threshold to 1 MiB and the mmap threshold to 4 MiB, so memory freed by
stopped processes does not stay in per-thread allocator arenas. A
`MALLOC_TRIM_THRESHOLD_` or `MALLOC_MMAP_THRESHOLD_` value in the sidecar's
environment replaces the matching setting.

All isolates share one copy of the V8 snapshot and of the runtime's
JavaScript bridge source. When a guest's event loop has received no work for
one second, the sidecar runs one memory-reducing garbage collection on its
isolate. It runs another only when the heap has doubled (by at least 8 MiB)
since the last one and at least 30 seconds have passed, so a guest that
serves requests with idle gaps does not pay for a full collection per gap.

The sidecar also keeps a pool of up to four pre-started V8 isolates so that
JavaScript and Python executions start faster. The pool stays resident while
the sidecar runs, at about 15 MiB per isolate. To cap it, set
`AGENTOS_V8_WARM_ISOLATES` to a value from `0` to `4` in the environment that
starts the sidecar. `0` disables the pool and trades memory for slower
execution starts.

The sidecar stores built V8 snapshots on disk so a new sidecar process does
not rebuild them: at most 16 files under `$XDG_CACHE_HOME/agentos/v8-snapshots`
(or `~/.cache/agentos/v8-snapshots`). Set `AGENTOS_V8_SNAPSHOT_CACHE_DIR` to
another directory, or to `off`, in the environment that starts the sidecar.
Script sources that snapshot-restored isolates share are kept while a cached
snapshot or a live isolate uses them, bounded to 64 MiB of copies. Unused
sources are freed first; when the sources in use leave no room, a new snapshot
fails with `ERR_AGENTOS_V8_SHARED_SOURCE_LIMIT` and processes load normally.

A helper process builds each snapshot. It is killed after 30 seconds
(`ERR_AGENTOS_V8_SNAPSHOT_HELPER_TIMEOUT`, and processes load normally), its V8
heap and its ArrayBuffer memory are each capped at 1 GiB, and its CPU time is
capped at the timeout. Set `AGENTOS_V8_SNAPSHOT_HELPER_TIMEOUT_MS` in the
environment that starts the sidecar to change the timeout.

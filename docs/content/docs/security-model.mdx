kernel-owned filesystem, process table, socket table, pipes, PTYs, permission

use their managed executors. Guest operations reach the host only through the
sidecar's policy-enforcing interfaces.

## Trust boundary

| Component | Trust | Responsibility |
| --- | --- | --- |
| Client | Trusted, except for submitted guest code and data | Chooses configuration, permissions, software URLs, and credentials |
| Sidecar, kernel, and VFS | Trusted enforcement point | Applies limits and permissions; owns processes, filesystems, sockets, and mounts |
| Executor | Untrusted | Runs guest JavaScript, Python, WASM, and third-party code |

The security boundary is **sidecar/runtime to executor**. A guest bypassing an
applied permission, mount boundary, egress rule, or resource limit is in scope.
A trusted client deliberately choosing a permissive configuration or unsafe
credential is not a runtime escape.

The sidecar runs in its own process, separate from your application. Guest code
and its memory never enter your application's process.

## What a VM can reach by default

A new VM behaves like a Docker container with no host mounts and no published
ports. Everything inside the VM works. Nothing crosses the VM boundary until you grant it.

| Resource | Default | How to grant access |
| --- | --- | --- |
| VM filesystem, guest processes, guest environment | Allowed | Restrict with the `fs`, `childProcess`, `process`, and `env` [permission](/agentos/docs/permissions) scopes |
| Guest listeners and loopback | Allowed, never bound on the host | Reach them from the host with `fetch`, `httpRequest`, or [previews](/agentos/docs/networking) |
| Host loopback services | Unreachable. Guest `127.0.0.1` is the VM's own loopback. | `loopbackExemptPorts`, one port at a time |
| Host files | Unreachable | [Mounts](/agentos/docs/filesystem#mounts), or copy files in |
| Host environment variables | Unreachable | The `environment` option |
| Host processes | Unreachable | None. Guest processes never become host processes. |
| Outbound network and DNS | Denied | [Network permissions](/agentos/docs/permissions#network). |
| Your backend and credentials | Unreachable | [Host functions](/agentos/docs/host-functions) you register, library only. Restrict them with the `hostFunction` scope. |

## Deny by default

Every operation that crosses the VM boundary needs explicit configuration:
external network access needs a network rule, host files need a mount, and
your backend needs a registered host function. Filesystem, process, and
environment scopes default to allow because they only reach the VM's own
namespace. The `hostFunction` scope also defaults to allow, so every host
function you register is callable until you restrict it. A scope can be
`"allow"`, `"deny"`, or a rule set that matches the operation and target.

## Host capabilities

Library VMs run under a trusted application, so the host may explicitly give a
VM access to host resources: host functions, host-backed mounts, external
sandboxes, and local software paths. Each of these runs with the host's
privileges. Expose them deliberately, and never pass guest-controlled values
into their configuration.

Host functions let a guest use a credential without seeing it. The handler runs
in your process with the secret, and the guest receives only the result. Treat
each host function as a public API: validate its input and authorize the call
inside the handler.

If your application lets untrusted users configure VMs, accept only
serializable configuration from them and resolve it against your own allowlist
of mounts and software sources.

## Hosted VM restrictions

The hosted `agentOS` actor accepts only serializable configuration. Its
filesystem descriptors are resolved through a fixed registry, and software
installation accepts only remote HTTPS `.aospkg` sources. It cannot receive:

- a host filesystem path or host-directory mount;
- a host-function callback, closure, or arbitrary host object;
- a custom filesystem or software resolver;
- an unregistered actor implementation or lifecycle hook.

Embedded Core runs inside a trusted application process and may explicitly
configure host functions, host-backed mounts, and local software paths. Those are
embedded capabilities, not actor capabilities.

## Isolation guarantees

- Guest processes are kernel-managed and never become host processes. Guest JavaScript runs inside V8; Python and WebAssembly use
  their configured executors, never a host Node.js process.
- Guest Node.js builtins such as `fs`, `net`, and `child_process` are
  implemented on the kernel. Guest code never reaches a real host builtin, and
  denied builtins throw `ERR_ACCESS_DENIED`.
- Guest sockets pass through the kernel socket table and applied network policy.
  Every address a hostname resolves to is checked against the policy, and a
  DNS answer that mixes allowed and blocked addresses fails as a whole.
- Trusted VM setup can update mounts and command stubs without relaxing guest
  filesystem permissions, including while a VM is running.
- Each VM's filesystem, process table, and runtime state are isolated from other
  VMs on the same sidecar. Handles are scoped to their VM, so a guest can't use
  another VM's sockets or capabilities, and each VM has its own quotas.
- Host-backed embedded mounts are confined to the configured root on every
  operation, including symlink and `..` resolution.
- Resource limits bound process count, descriptors, sockets, filesystem bytes,
  runtime memory, CPU time, queues, payloads, and waits.
- Limit pressure is logged or emitted as a structured warning; exhaustion fails
  with a typed error naming the limit and how to raise it.

## Operator responsibilities

- Authenticate and authorize clients before they receive an actor connection.
- Keep object-store credentials and operator package-download settings outside
  actor-readable durable configuration.
- Choose permissions and resource limits for the workload.
- Treat software URLs and config as trusted control-plane input, while treating
  the downloaded bytes and executed code as hostile.
- Set timeouts and CPU limits on code you did not write.
- Harden the host or container that runs the sidecar, and run it as a non-root
  user. Rivet Cloud runs the sidecar unprivileged under gVisor.
- Give each mutually untrusted tenant its own VM.

See [Permissions](/agentos/docs/permissions),
[Resource Limits](/agentos/docs/resource-limits), and
[Filesystem](/agentos/docs/filesystem) for the public configuration surfaces.

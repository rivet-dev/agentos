---
title: "Hosted Actor Limits"
description: "Reference the payload, collection, replay, timeout, and cache limits enforced by the hosted agentOS stack."
---

By default, every action is bounded below the hosted worker's 1 MiB encoded message ceiling. Limits
apply to the complete encoded request or response. Encoding overhead means a
payload should not be constructed to exactly equal the message ceiling.
The actor reserves 1 KiB for RivetKit's envelope and checks the encoded result,
including batch paths, errors, and JSON string escaping. A batch can therefore
reach the message limit before reaching its content-byte limit.

Hosted actor and preload policy budget rejections use RivetKit's public `user` error group and the stable `limit_exceeded` code. Their `metadata.budget` names the setting, observed quantity, limit, units, and remediation. Check the code and budget setting rather than parsing the message. Both clients receive this actionable message and metadata without internal cause chains or request contents; unrelated errors retain their existing masking.

Known VM filesystem byte and inode quota rejections also use `user/limit_exceeded`. Their `metadata.limit` contains `setting`, `limit`, `observed`, `units`, and `remediation`; `limit` and `observed` are always exact decimal strings, including small values. Parse them with `BigInt` in TypeScript rather than converting them to `number`. The observed value is the projected filesystem total, not the requested increment. These diagnostics name `limits.resources.maxFilesystemBytes` or `limits.resources.maxInodeCount` and remain independent of actor transfer budgets. Ordinary backend disk-full errors and unrelated internal errors keep their existing handling. Guest filesystem operations continue to receive `ENOSPC`.

Operators can raise the worker's admission, message, codec, and whole-file transfer budgets at startup:

```bash
agentos-sidecar actor --actor-budgets-json '{"admission":{"maxConcurrentActions":80},"transport":{"maxMessageBytes":8388608},"codec":{"maxBinaryBytes":2097152,"maxInputValues":2097152},"filesystem":{"maxTransferBytes":2097152}}'
```

Omitted fields keep the defaults below. The JSON also accepts `codec.maxInputDepth`. Unknown fields, invalid zero values, and values outside the transport or platform representation are rejected before worker startup. Zero is valid for `cron.maxHistory` and `filesystem.maxRecursiveDepth`; other capacities must be positive. The first successful startup configuration freezes the process policy. Apply the same setting to each worker and restart workers to change it. These settings do not change `config.limits`, VM filesystem quotas, gateway limits, or independent filesystem backend frame limits.

Existing Rust and TypeScript filesystem actions can write and read larger finite files under these budgets; no new client API or streaming protocol is required. A caller's `maxBytes` must fit `filesystem.maxTransferBytes`, while binary tags and encoded messages must independently fit their codec and transport budgets. Raise them with enough headroom for base64 and envelope overhead. The current Rust client represents byte content as numeric arrays, which also consume one input value per byte; raise `codec.maxInputValues` for those transfers. TypeScript binary tags consume fewer structural values. The example allows both representations without changing either client encoding. Whole-file reads still return the complete file before the actor checks its reply budget; VM read/allocation policies remain in force. Streaming is unavailable, so these options provide a larger finite ceiling rather than unlimited file transfers. Errors name the owning setting and tell the operator how to raise it.

The default registry uses this immutable worker policy. Rust applications building a custom registry can call `configure_process_actor_budgets` before registration and use `agentos_actor::hosted_actor_config()` for the actor's RivetKit registration. A conflicting configuration after the first successful configuration or policy consumption is rejected; existing actors never change policy mid-action. Startup options also accept the following validation groups. Omitted fields retain the table's defaults; these settings do not raise VM permissions or resources.

Names ending in `Bytes` measure UTF-8 or encoded bytes as applicable; `Ms` measures milliseconds. Other fields count their named entries, arguments, packages, contexts, diagnostics, rules, values, mounts, sources, or terminal columns/rows. Process cwd keeps the separate argument-byte budget, which defaults to 16 KiB; language cwd uses the 4 KiB path default. Raising a timeout ceiling does not extend the unchanged six-minute actor action deadline. Omitted synchronous execution timeouts select the corresponding worker ceiling; explicit lower `timeoutMs` remains lower. Spawned language processes retain the existing omitted-timeout behavior, and process/terminal wait actions retain their 30-second polling window.

Saved desired configuration is validated against the worker policy before runtime activation. If a later worker has tighter ceilings, activation rejects the out-of-budget saved value with the owning setting; it does not truncate or rewrite the saved document. A larger worker ceiling does not alter explicit saved values. New preview policy defaults select the worker preview ceilings; explicit saved lower values remain lower. Raising the worker alone does not raise those saved values. Runtime issue retention evicts the oldest issue at capacity. Cron errors retain a UTF-8 prefix under `maxErrorBytes` and append the existing ellipsis when truncated. Cron history remains scheduler-owned: `maxHistory` is the worker ceiling, while each schedule can select a lower history including zero. Omitted cron history remains 32, and an omitted fetch-stream read remains 64 KiB. If a worker ceiling is lower than either default, callers must explicitly select a fitting value. No new knob changes these caller defaults, and no new streaming action is introduced. The current generated preview token is 32 characters; a smaller `network.maxPreviewTokenBytes` rejects creation before storing a lease. `filesystem.maxRecursiveDepth` bounds an explicit `maxDepth`; omission keeps the existing Core behavior and the VM recursive-filesystem resource policy rather than selecting a new actor depth default.

Keep RivetKit's default `encoding: "bare"` for binary file, network, and replay
results and exact integer fields.
Uploaded `Uint8Array` values use a base64 wrapper even inside BARE arguments,
so keep payloads below the configured binary ceiling (768 KiB by default) with headroom for that wrapper and the
action envelope. The actor decodes the wrapper before applying each action's
content-byte limit. Integer action fields accept `bigint` when exact values
exceed JavaScript's safe integer range; do not coerce returned revisions,
generation IDs, or cursors to `number` without checking that range.

The actor deadline limits how long an action can wait; it is not itself proof
that guest work stopped. `process.run` requests `SIGKILL` when its run timer
expires. It returns `timeout` only after observing the guest exit event. If
launch never acknowledges, or the exit cannot be confirmed within 30 seconds,
it returns `termination_failed` instead. Cancelling the actor action starts a
best-effort cleanup task that waits for exit and logs confirmation failures,
but cannot confirm exit to the cancelled caller. A launch accepted after cleanup
expires may still start; inspect or restart the VM before assuming execution has ended.

Sidecar-originated limit errors and VM-disposal timeouts expose structured
details in the actor error's `metadata.limit`, including `limitName`,
`configuredLimit`, `unit`, `operation`, and `configurationPath` when available.
An actor-side deadline can return `timeout` without those sidecar details;
it does not confirm that remote teardown completed.

The package cache and preload limits are operator settings. Actor creation
input cannot raise them. VM resource limits under `config.limits` are caller
overrides, subject to sidecar hard limits.
The package-mount limit counts the entire live VM projection: boot packages,
packages installed later, command and manpage aliases, and directory leaves
from `provides.files`. It does not count unrelated filesystem mounts. A boot
configuration or install that would exceed the limit fails before changing
mounts. The sidecar warns when the projection reaches 80% of the configured
limit and returns a structured resource-limit error naming the override.
Installed mounts count until the package is uninstalled, even if a local
package source changes or disappears. Uninstall releases that capacity and
does not require spare mount capacity.
An isolated temporary cache is removed when the standalone worker shuts down
normally; forced termination and host crashes require host temporary-directory
cleanup. Persistent cache directories must be distinct for concurrent workers.

Startup advisory preloading defaults to a 10 second process deadline, a 1.5
second coordinator-plan read timeout, 64 plan entries or 2 GiB, and four
concurrent downloads. Usage observations are coalesced into at most 128 entries
and flushed every five minutes. Operators can change these process settings
before starting the actor; the maximum startup deadline is five minutes, the
plan read timeout is one minute, and the plan format caps entries at 512 and
predicted bytes at 64 GiB. Preload timeout never waives the required-package
readiness check. If VM initialization times out, the actor reports `timeout`
and starts cleanup of any VM created before or just after the deadline. Check
`vm.status` for a failed or degraded state before retrying.

Files and exports exceeding the configured finite ceilings must use bounded application-level pieces where the application supports them, or a separate object-transfer service. Hosted workers can raise the startup budgets above the defaults; this does not expose a host mount. Native backpressured action streaming remains unavailable.

Near-capacity runtime conditions emit `vm.limitWarning`. A rejected operation
returns `limit_exceeded` with the observed limit and the setting that controls
it when that limit is configurable.

Replay retention and pagination are enforced once in Core for both processes
and terminals. The actor forwards the requested cursor and bounds; an invalid
page limit returns structured `limit_exceeded` metadata from Core rather than
being reinterpreted by the actor.

## Embedded API

Embedded Core does not have the actor's 1 MiB action envelope, but its VM,
sidecar, package, queue, and resource limits still apply. Read more in the
[embedded API quickstart](/agentos/docs/quickstart-embedded).
